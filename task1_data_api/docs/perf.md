# Task 1 性能说明：大数据量与高并发推演（只推演，不压测）

> 现状基线：288 行明细、111 行预聚合、API P99 < 5ms（本机）。以下按数据量逐级推演。

## 1. 数据量分级推演

| 数据量 | 存储形态 | 查询路径 | 瓶颈判断 |
|---|---|---|---|
| ≤ 10 万行（当前量级 ×300） | 单文件 DuckDB | 直接扫明细也够（列存+向量化），预聚合仍首选 | 无 |
| 10 万 ~ 5000 万行 | 保留预聚合表；dwd_fact_sales 加分区 | API 只打 dws_sales_daily（行数 = 天数×平台数×2，千级） | 在线路径不变，靠的是**聚合表与明细表解耦** |
| > 5000 万行 / 多机 | 迁 ClickHouse | `ORDER BY (platform, dt_local)` 排序键 + 按月分区；查询谓词命中排序键前缀 → 稀疏索引裁剪 99% 数据 | 迁移只改 DDL，SQL 方言几乎不动 |

**核心论点**：把"大数据量"问题在**离线聚合层**解决，而不是让在线 API 聪明地扫大表。dws_sales_daily 的行数由时间跨度决定（3 年 ≈ 1.5 万行），与原始销量行数无关。

## 2. 高并发推演（读多写少，QPS 100 → 10000）

1. **缓存（已实现）**：cachetools TTLCache（1024 条目 / TTL 60s），key = 参数排序后 md5。命中直接返回，不打 DB。命中代价 O(1)。
2. **生产换 Redis（key 设计不变）**：`trend:{start}:{end}:{platforms}:{gray}`，多 worker 进程共享缓存；TTL 60s 内的趋势查询全部击穿缓存保护层。⚠️ 明确取舍：缓存以 60s 数据新鲜度换吞吐，日粒度趋势完全可接受。
3. **无状态水平扩展**：API 进程不持有状态（缓存可外置），uvicorn workers × N + Nginx/LB 即可线性扩；DuckDB `read_only=True` 支持多读连接。
4. **写路径隔离**：摄取与聚合是离线批任务（可日调度），与在线查询物理隔离——并发压力不会传导到写侧。

## 3. 冷热数据与分区

- 热数据（最近 90 天）与冷数据分区存放：ClickHouse 按月分区天然支持；查询带日期谓词时分区裁剪避免扫冷分区。
- 冷数据归档：按月导出 Parquet（列存、压缩比高），需要时 DuckDB 可直接 `read_parquet` 查询——不需要回灌数据库。

## 4. 明确不做的（取舍）

- **不引入 Redis/ES/ClickHouse 到 demo**：288 行数据上它们是负资产；但 schema/接口按其生产形态设计，迁移是改 DDL 而非重写。
- **不做实时聚合**：日趋势业务下，T+1 预聚合 + 60s 缓存足够；"实时"需求出现时再上流式（成本收益另算）。
- **不压测**：QPS/P95 数字在 288 行数据上没有意义，压测是给生产容量规划用的；推演链路已覆盖面试问题"数据到 1 亿行怎么办"。
