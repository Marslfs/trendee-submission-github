## 0. 一句话结论（先看这个）

这份笔试题不是"考算法"，而是**把岗位真实工作切片成两道题**：Task 1 考"多源脏数据 → 可被高并发查询的销量 API"（数据工程主线），Task 2 考"PDF → 可溯源可引用的内容生产"（RAG 主线）。

对应 JD 原话"Data Engineering × NLP × LLM × Retrieval 交叉位置"，**两道题分别对应 JD 的前 4 条职责和后 4 条职责**，评分权重几乎 1:1。写方案时最大的加分点不是技术多新，而是：**每个决定都能说出"为什么不选另一个"**。

**岗位介绍（原文）**

> 我们正在寻找一名兼具数据工程、数据分析与 AI/NLP 能力的 AI 数据工程师。你将负责数据处理、建模、存储、分析与服务体系建设，保障数据的准确性、一致性、实时性和可扩展性；同时结合 NLP、Embedding、RAG 和 LLM 等技术，将结构化与非结构化数据转化为可分析、可检索、可被 AI 系统稳定使用的数据与知识资产。

**岗位职责（8 条，原文）**

1. 负责数据清洗、转换、去重、归一化、聚合及数据质量处理，建设稳定的数据处理 Pipeline，支持批量及增量数据处理。
2. 负责数据模型、Schema、索引及存储架构设计，根据不同业务场景合理选择和使用数据库技术。
3. 深入使用数据库系统，进行数据建模、查询优化、索引设计和性能优化，保证数据系统稳定性、准确性和扩展性。
4. 负责业务数据分析、指标体系建设、趋势分析和异常分析，从数据中发现问题并支持业务决策。
5. 建立数据质量管理和监控机制，包括数据完整性、一致性、准确性检查，以及异常检测和实时预警。
6. 结合 NLP、Embedding、LLM 等技术处理非结构化数据，包括信息抽取、文本分类、实体识别、实体匹配和结构化输出。
7. 参与 RAG 与检索系统建设，包括文档解析、Chunk、Embedding、检索、Reranking、Metadata 和数据溯源。
8. 将数据处理、查询、分析和检索能力封装为 API 或数据服务，为 AI 应用提供可靠的数据能力。

**任职要求（8 条，原文）**

1. 扎实的 Python 和 SQL 能力，具备良好的工程开发习惯。
2. 熟悉 PostgreSQL、MySQL、Elasticsearch、ClickHouse 等一种或多种数据库，并理解不同数据库的适用场景。
3. 深入理解数据建模、Schema 设计、Index、Partition、Aggregation、Query Optimization、Cache 等数据工程能力。
4. 具备较强的数据分析能力，能够完成数据统计、指标设计、趋势分析和异常分析。
5. 重视数据准确性和数据质量，对数据口径、重复数据、异常值、缺失值和数据验证有系统处理经验。
6. 具备大规模数据处理经验，能够考虑数据增长情况下系统性能和可扩展性。
7. 具备 NLP 或 LLM 项目经验，了解 Embedding、RAG、信息抽取、文本分类、实体识别等技术。
8. 具备较强的问题分析能力，能够独立定位并解决数据、数据库及系统性能问题。

**加分项（6 条，原文）**

- 有 Elasticsearch / ClickHouse 大规模数据集项目经验。
- 有实时数据处理、数据监控或异常预警系统建设经验。
- 有 RAG、搜索、推荐或企业知识库项目经验。
- 熟悉 FAISS、Milvus、Qdrant、pgvector 等向量数据库。
- 有 Entity Resolution、Entity Matching 或 Knowledge Engineering 经验。
- 有高并发数据 API 或数据服务开发经验。

**岗位特点（原文）**

> 这是一个位于 Data Engineering × NLP × LLM × Retrieval 交叉位置的工程岗位。我们希望候选人不仅能够处理数据，更能够理解数据价值，建设准确、稳定、可扩展的数据系统，并推动数据在 AI 应用中的实际落地。

### 1.2 岗位画像：他们真正在招什么人

一家做 **GEO（生成式引擎优化）** 的公司，核心产品把"品牌资产"变成"AI 能读懂、能引用、能长期记住的结构化知识"。这条业务链上有两个数据刚需：

1. **供给侧**：抓取、清洗、归一化全网商品/内容数据（多平台、脏、重复、标题不规范）→ 需要有 OLAP 思维的数据工程能力；
2. **消费侧**：把文档变成可检索、可溯源、可被 LLM 稳定引用的知识→ 需要 RAG 工程能力。

所以这不是"写 SQL 的"也不是"调 API 的"，而是**一个人要把"数据管道"和"知识管道"都建起来**。JD 里"AI 系统稳定使用""数据溯源"这两个词，直接对应笔试题 Task 1 的"查询口径"和 Task 2 的"引用溯源"。

## 3. 样例数据摸底（我实际跑过一遍的事实）

> 这一节不是题目要求，但写方案前必须先知道数据长什么样。以下数字均为对 `样例销售数据.xlsx` 的真实统计。

### 3.1 结构

| 字段          | 类型            | 说明（来自 `field_notes` 工作表）                           |
| ----------- | ------------- | -------------------------------------------------- |
| product_id  | 原始 ID         | 同一商品可能在不同日期、平台重复出现                                 |
| title       | 文本            | 含大小写、连字符、空格、词序、近义表达差异                              |
| sales_count | 整数            | 该条原始记录的销量                                          |
| timestamp   | 数值（Excel 序列号） | 需自行考虑日期聚合、跨月边界与时区                                  |
| user_id     | 文本            | 示例来源记录标识                                           |
| category    | 文本            | 粗粒度：dress / shirt / shoes / pants / skirt / jacket |
| source      | 文本            | website / app / marketplace                        |

`field_notes` 明确写了："不提供标准答案。候选人需要自行定义 maxi dress 的识别/归一化规则，并在方案中说明理由。"

### 3.2 关键事实（写方案直接引用）

| 观察     | 实测值                                                    | 对方案的含义                                  |
| ------ | ------------------------------------------------------ | --------------------------------------- |
| 总行数    | 300                                                    | 数据量小，**性能不是跑出来的，必须靠设计讲出来**              |
| 去重后商品数 | 30 个 product_id                                        | 可按商品建维度表                                |
| 标题写法数  | 37 种写法 / 30 个商品                                        | 证明必须做归一化，不能按 title 直接 group             |
| 平台分布   | app 101 / website 100 / marketplace 99                 | 三平台近似均匀，适合做平台对比图                        |
| 类目分布   | dress 174、skirt 33、shoes 33、pants 28、shirt 27、jacket 5 | 只有 dress 可能命中 maxi dress，其余应被排除         |
| 完全重复记录 | **12 组，各重复 2 次（共多出 12 行）**                             | 5 个字段全同，属采集重复，需幂等去重                     |
| 时间范围   | 2024-01-01 07:00 ~ 2024-03-13 09:45（按序列号直读）            | 覆盖 1–3 月，3 月只到 13 日                     |
| 月度分布   | 1 月 130 / 2 月 124 / 3 月 46                             | 做趋势图时 3 月不完整，需注明                        |
| 夜间记录   | **60 条落在 20:00–04:00 之间**                              | 这是"时区陷阱"：+8 小时后日期会跨天                    |
| 最早时间   | 2024-01-01 07:00                                       | 说明源数据更像 **UTC 存储的本地时间**，需显式声明时区口径       |
| 销量范围   | 1–18 之间整数，无缺失、无负数、无异常值                                 | 题目说的"异常记录"实际藏在**时间和重复**里，不在 sales_count |

### 3.3 标题归一化的"坑"（这题的核心考点）

同一 product_id 的多种写法：

| product_id | 标题变体                                                     | 陷阱        |
| ---------- | -------------------------------------------------------- | --------- |
| 2001       | `Maxi Dress Floral` / `maxi dress floral`                | 仅大小写      |
| 2002       | `SUMMER MAXI DRESS` / `Summer Maxi Dress`                | 全大写       |
| 2003       | `Red Maxi Dress` / `Red Maxi-Dress`                      | 连字符       |
| 2004       | `Blue Maxi Dress` / `blue maxi  dress`                   | 双空格       |
| 2005       | `Floral Maxi Dress` / `Floral long maxi dress`           | 词序 + 插入词  |
| 2008       | `Denim Maxi Dress` / `Maxi Denim Dress`                  | 词序调换      |
| 2010       | `Women's Maxi-Dress Floral` / `Womens Maxi Dress Floral` | 所有格 + 连字符 |

**必须区分的负样本**：

- `Maxi Skirt`、`Long Floral Skirt`、`Pleated Midi Skirt` → 有 maxi 或 long，但**不是 dress**（若只按 `maxi` 关键词匹配会误杀）
- `Mini Dress Black`、`Summer Mini Dress`、`Midi Dress Blue` → 是 dress，但**不是 maxi**（若只按 `dress` 匹配会误杀）
- `T-shirt Dress`、`Casual Dress` → dress 但不含 maxi，应排除
- `Elegant Long Dress` → **灰区**：无 maxi 关键词，但长裙语义接近，建议放入 gray_zone 表并显式说明"默认不纳入"或"可配置纳入"

**可跑通的判定规则（已在本机验证：命中 12 个商品、1,137 件销量 / 全量 2,840 件）**

```
1. 归一化：小写 → 连字符/标点替换为空格 → 压缩多空格 → 去首尾 → 可选：去停用词(women's/womens/the)
2. 词元集合匹配：tokens ∩ {"maxi"} ≠ ∅  且  tokens ∩ {"dress"} ≠ ∅
3. 负向排除：tokens ∩ {"mini","midi","shirt-dress","tshirt"} ≠ ∅ → 排除
4. 灰区：tokens ∩ {"long"} ≠ ∅ 且 不含 maxi → 进 gray_zone，默认不计入，可通过参数 include_gray_zone=true 打开
5. 输出：matched / gray_zone / excluded 三分类，落表便于审计
```
